# 严重级别、置信度与 findings 结构

本文件是阶段②写 findings.json 时的定级口径。severity 与 confidence 的取值只能取自下表，
不得自造第三个字面量——渲染器按字面量分栏展示，文档与代码不一致会静默漏项。

## 严重级别

| 级别 | 定义 | 典型例子 |
|---|---|---|
| P0 | 硬伤，可能导致废标或事实错误 | 同一文件混用多个主体名称、金额合计与分项不符、引用了不存在的编号 |
| P1 | 严重问题，影响评审判断 | 前后矛盾、同一主体多种名称写法、错别字改变原意、货币单位混用 |
| P2 | 体例与格式不一致 | 字体字号不统一、行距不一致、标题编号体系混用、图表题注写法混用、日期格式不统一 |
| P3 | 优化建议 | 表述可更精炼、缩写未给全称、术语未统一 |

判定原则：先看是否影响评审结论，再看是否影响可读性，最后才是风格偏好。

## 置信度

| 取值 | 含义 |
|---|---|
| 确定 | 有程序化依据，或有文档内明确证据链。确定性检查产出的一律为确定。 |
| 疑似 · 需人工核实 | 仅由模型语义推断，或需要外部事实才能确认。 |

主体名称「同一主体多种写法」为确定。「疑似混主体」为疑似 · 需人工核实。

判定口径：

- 能在文档里指出两处互相冲突的原文，或有算术、编号上的硬依据 → 写确定。
- 结论依赖文档外的事实（企业是否真实存在、被引文献是否真实存在、法规是否现行有效）→ 写疑似 · 需人工核实。
- 拿不准时写疑似 · 需人工核实。错标成确定的代价比漏报高：确定级别会被当作已核实的事实直接使用。

## consistency.json 里的阶段① 结论

阶段①的结论写在 consistency.json 里。**语义层的 confidence 不以阶段①有没有对应依据为准**：
阶段①只做格式与体例检查，不产出前后矛盾、错别字、引用张冠李戴这些语义类别，
拿阶段①当门槛会让语义层永远写不出「确定」，把本可确定的发现全部降级成「疑似 · 需人工核实」。

consistency.json 的键：

| 键 | 内容 | 怎么用 |
|---|---|---|
| style_profile | 各项样式（西文字体、中文字体、字号、对齐、缩进、行距、段间距）的主流值、出现次数与参与统计的段落数 | 判断「这段与全文主流写法不一致」时对照它 |
| issues | 确定性层已报的问题列表 | 这里已有结论的问题不要再写进 findings.json |
| entities.names | **按规范核心字号归并后**的主体清单：**核心字号相同**的主体只有一条，取该主体最先出现的写法作为 `name`，另附 `core`（规范核心字号）、出现次数、涉及文件 | 判断「这个名字是不是本文档的主体」。注意归并的键是**核心字号**，不是「是不是同一家公司」——核心字号不同、但被归组规则判为同一主体的两种写法，在这里仍是**两条**（各带一个 `core`），要到 `entities.variants` 里才合成一条 |
| entities.variants | 按主体归并后的写法变体分组（names 是原始写法，canonicals 是去掉连接词后的规范写法）。同一主体的另一种写法只出现在这里。分组里的 `core` 与上一行的 `core` 是**同一个口径**（都是规范核心字号，保留行政区划），但**取值未必相同**：一组的 `core` 取该组成员里**最长**的规范核心字号 | 判断「这几个名字是不是同一家公司」 |
| entities.per_file | 每个文件抽到的主体名（取的是**还原名**，不是裁剪后的残缺名），按出现顺序排列。**只在同一段文字内部去重**，跨段落不合并：同一个名字在文件里出现三次就会列三次 | 判断「这一句里的名字与该文件其余部分是否一致」。要做集合比较时自己先去重 |
| stats | 文档数与问题数 | 了解本次规模 |

阶段①不做算术校验，合计与分项是否相符只能由语义层自己判断。

**主体名清单里没有的名字，不等于文档里没有这家公司。** 抽取器有三种已知情况会让主体名与原文对不上：整家公司被丢掉（通用片段的判定用的是**裁剪后**的名字，还原名即使算对了也扔掉）、两家公司被并成一个名字（角色词前面带填充词时，条款 (b) 要求的「角色词位于名字串开头」不成立）、还原名还原出的是一段句子碎片（条款 (b) 的第三条守卫只检查那一段**是不是以行政区划或国家前缀开头**）。**判定「某个主体名是不是本文档的主体」时不能只看 `entities.names`**——清单本身就是有缺口的，要回原文确认。

**consistency.json 与输入顺序无关**：同一批文档换个 `--files` 顺序跑，写出来的 consistency.json 逐字节相同（文档按文件名排序后分析，问题列表、主体清单、写法变体都按稳定键排序）。否则复查对比（§6）会凭空多出「新增问题」与「已修复问题」——文件没变，结论却变了。

## findings.json 结构

```json
{
  "severity": "P1",
  "category": "前后矛盾",
  "detector": "llm",
  "confidence": "确定",
  "file": "a.docx",
  "locator": {"type": "paragraph", "index": 42, "section_path": "第三章/3.2 报价说明"},
  "quote": "原文摘录",
  "description": "问题描述",
  "suggestion": "修改建议"
}
```

字段说明：

| 字段 | 说明 |
|---|---|
| id | **可省略，不要自己编。** 这是派生字段：由 file + category + locator + quote 哈希得到的 16 位指纹，渲染器在读入 findings.json 时自己算并重算。同一问题在文档未改动时保持稳定，用于复查对比。 |
| severity | P0 / P1 / P2 / P3 |
| category | 问题类别。**只能取固定清单里的中文类别**：语义层九个（错别字用词、标点格式、前后矛盾、主体名误用、引用张冠李戴、待补充内容、数字逻辑、表述不清、术语一致性，见 content-rules.md），确定性层的十一个类别——字体一致性、段落格式一致性、标题层级体例、图表题注体例、表格体例、列表与编号、引用标记、数字与单位、主体名称、主体串写、术语与缩写——由脚本产出，**不要在 findings.json 里写**。校验按这张固定清单逐字比对（清单在 `scripts/categories.py`）：`typo错别字`、`format 格式`这类中英混写、以及清单外的自造标签，都会让 findings.json 校验失败并以非零退出码退出，不会被当成「未分类」混进报告 |
| detector | deterministic 或 llm。模型写出的必须是 llm。 |
| confidence | 确定 或 疑似 · 需人工核实 |
| file | 文件标识，与 docs.json 中的 file 字段一致。同名文件在不同目录下时，file 是相对路径（如 `a/report.docx`），照抄原样即可，不要截成文件名 |
| locator | 定位信息，type 取 paragraph / table / file / section |
| quote | 原文摘录，尽量取完整的句子或短语，不要改写。**它就是有问题的那一段**，报告里会被高亮标出 |
| description | 问题描述，说明为什么不妥 |
| suggestion | 可直接执行的修改建议，不要写「建议优化」这类空话 |

写入规则：

1. 只输出真实存在的问题。没有问题就不写条目，不要为了凑数编造。
2. quote 必须是原文中确实存在的片段。
3. locator.index 用 chunks.json 中 block_indexes 的首个下标。
4. 同一问题只写一条，不要在不同类别下重复。
5. id 不必写。渲染器按 file + category + locator + quote 自行计算，你写了也不作数。
