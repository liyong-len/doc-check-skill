# doc-check 技能设计说明

日期：2026-11-07
状态：待评审

## 1. 背景与目标

投标场景下常常需要同时撰写多份文档。这些文档由不同人或不同时间段完成，容易出现格式不统一、错别字、企业名称写错、引用依据张冠李戴、文件体例混乱、前后矛盾、待补充内容缺失等问题。当同时为多家主体准备材料时，还会出现把不同企业的信息写混的情况。

本项目要交付一个可上传至 GitHub 的技能（skill），供同事在任意智能体上（Claude Code、Codex CLI、WorkBuddy、DSH，以及其他能够执行脚本并读写文件的智能体）一键安装，用于对一份或多份既有文档做系统检查，产出可阅读的检查报告。

设计目标：

- 检查过程尽量确定性。格式、体例、字体字号、编号体系、主体名称这类可由程序判定的问题，一律由脚本判定，不交给模型自由心证。
- 跨智能体行为一致。同一批文档、同一深度档位，在不同智能体上应得到相同的确定性结论。
- 只读。绝不修改用户原文档。
- 报告可离线阅读、可转发、可归档。
- 安装门槛低。同事跑一条命令即可完成安装。

## 2. 范围

### 2.1 支持的文件格式

| 格式 | 抽取内容 | 格式检查置信度 |
|---|---|---|
| docx | 段落文本、标题层级、样式指纹、列表编号、表格、页眉页脚、节设置 | 高 |
| xlsx | sheet、单元格值与样式、合并区域、表头行推断 | 高 |
| pdf | 逐页文本、字体名与字号统计、表格抽取 | 低，报告标注「版式不可靠」 |
| md / txt | 标题层级、列表、表格、代码块 | 无样式概念，格式类检查项标为「不适用」 |

### 2.2 明确不做的事

- 不修改、不回写任何用户文档。检查结果只以报告形式输出。
- 不联网核查。企业名称是否真实存在、引用文献是否真实存在、法规是否现行有效，均不在本工具能力范围内，相关问题一律标注为「需人工核实」。
- 不调用外部大模型 API。语义判断由运行技能的那个智能体自身完成。
- 不做 OCR。扫描版 PDF 会被明确标记为「需 OCR，当前不支持」。

### 2.3 事实依据的边界

本工具只做文档内互查。可以查出的是「同一个东西在文档内的多种写法不一致」「同一事实在两处描述冲突」「文中出现了疑似属于另一主体的名称」。

不能查出的是「这个名称对应的企业在现实中并不存在」「引用的这篇文献是杜撰的」。凡涉及外部事实的判断，一律标注置信度为「疑似 · 需人工核实」，报告附录中固定声明这一点。

## 3. 总体架构

采用双层架构：脚本层负责确定性抽取与统计，智能体层负责语义判断。

```
① 确定性  python scripts/prepare.py --files <paths...> --depth standard --work .doc-check-work
              ↓
              work/docs.json         每份文档的结构化内容与样式指纹
              work/consistency.json   确定性检查结果
              work/chunks.json        分片，含邻接上下文与预标注
              work/manifest.json      文件清单、统计、指纹、版本
              ↓
② 语义    智能体读 chunks.json 与 references/content-rules.md
              ↓
              work/findings.json      语义检查结果
              ↓
③ 渲染    python scripts/render.py --work .doc-check-work --out report.html
              可选 --baseline <上次 findings.json>，报告追加复查对比章
```

三阶段协议是跨智能体的唯一契约。它只要求智能体具备三项能力：执行 Python 脚本、读取 JSON 文件、写入 JSON 文件。任何具备这三项能力的智能体都能执行本技能，不依赖特定厂商的专有特性。

智能体在阶段②之前不做任何形式的前置准备，也不自行读取原始文档。所有输入必须来自阶段①产出的 JSON，以保证不同智能体看到的信息完全相同。

## 5. 阶段①：抽取与统计

### 5.1 样式指纹

样式指纹是格式一致性检查的基础。定义为归一化元组：

```
(西文字体, 中文字体, 字号pt, 加粗, 斜体, 对齐, 左缩进, 首行缩进, 行距, 段前距, 段后距)
```

抽取器对每个段落计算指纹，按文件统计频次，再跨文件汇总。出现频次最高的取值称为主流值，其余为偏离项。偏离项在报告中逐条列出文件名、段序、实际取值与主流取值。

比对单位是「段落」，因为段落是格式差异在文档中最直接的体现单元。对表格单元格、标题、列表项也计算同一套指纹，但分表统计，避免正文与表格的正常差异被误报。

### 5.2 各格式抽取细节

**docx**：使用 python-docx。遍历正文段落与表格，读取段落样式名、对齐、缩进、行距、段间距、字体（区分 ascii 与 eastAsia 属性）、字号、加粗、斜体。读取编号定义用于判断列表编号方式。读取表格的单元格文本与单元格级样式、合并情况。读取页眉页脚文本与节设置（纸张、页边距）。

**xlsx**：使用 openpyxl。遍历所有 sheet，读取每个非空单元格的值、字体、填充、边框、数字格式、对齐方式；记录合并区域。推断表头行（首行非空且下方存在数据的行）。跨 sheet 与跨文件的列名集合差异比较尚未实现。

**pdf**：使用 pdfplumber。逐页提取文本，按字符统计字体名与字号分布，按页提取表格。由于 PDF 不携带可靠的样式语义，其格式类结论一律标注置信度为低。

**md / txt**：解析标题层级、列表、表格与代码块。格式类检查项在该类型下统一标为「不适用」。

### 5.3 确定性检查清单

analyze.py 产出十类检查结果，全部写入 consistency.json（第 6 类主体名检查产出两个类别：
写法不统一报「主体名称」，疑似混主体报「主体串写」，因此报告的规则表里是十一个类别）：

1. **字体字号一致性** — 列出偏离主流字体的段落与偏离主流字号的段落
2. **段落格式一致性** — 行距、缩进、对齐、段间距的偏离项
3. **标题层级体例** — 层级跳级（如 H1 直接跳 H3）、编号体系混用（`1.` / `一、` / `第一章` 同时出现）
4. **图表题注体例** — 图与表分开比较：`图1-1` / `图 1-1` / `图1.1` 等写法混用（数字前有无空格算两种写法）；图表编号不连续，按 (对象类型, 章) 分成两条序列各自查缺号。不检查英文题注（`Figure` / `Table`）
5. **表格体例** — 各表首行的加粗写法不统一（docx 与 xlsx 都在内）。跨页表格缺少重复表头不做，需人工核对
6. **主体名一致性** — 见 5.4
7. **数字与单位** — 元与万元混用、日期格式不一。金额小数位不一与百分号缺失不做
8. **引用标记** — `[1]` / `文献[1]` 等写法混用。`（1）` 要求前面有引用引导词（参考文献、文献、见、据……）才算引用标记，否则中文枚举序号会大量误报。编号越界与参考文献表缺项不做，需人工核对
9. **列表与编号** — 有序列表编号方式混用
10. **术语与缩写** — 缩写首次出现时未给出全称

第 5、7、8 条里点名的三项**不在本版本范围之内**：跨页表格缺少重复表头（docx 抽取器不读 `w:tblHeader`，实现不了）、金额小数位不一与百分号缺失、引用编号越界与参考文献表缺项。这三项需要人工核对，§14 有记录。报告 §7 的规则表只声明真正跑的检查，不声明这三项。

### 5.4 主体名自动发现

用户不提供外部依据，因此主体信息完全从文档内推导。流程如下：

主体名与缩写的发现**读表格单元格**，与 chunk.py 分片时读表格文字的口径一致：只在表格里写出协作方或术语表的文档，确定性层与模型层看到的实体集合必须一致。

1. 用正则匹配公司类名称（`××有限公司`、`××集团`、`××研究院`、`××事务所` 等词尾形式），覆盖中英文括号与常见全角半角混排。`中心` 不作为企业形式词——它是普通名词，投标文档里的「技术中心」「研发中心」 ubiquitous，若当作形式词会凭空造出第二个主体字号，触发假的 P0「疑似混主体」
2. 对每个匹配结果归一化：去除空白与全角半角差异、统一括号
3. 按归一化结果聚类，同时按规范核心字号再聚一次，用来发现同一主体的不同写法，例如「北京华信科技有限公司」与「北京华信科技有限责任公司」归为同一核心字号但属于不同写法变体。规范核心字号 = 去掉公司词尾（只剥企业形式词）与开头的弱连接词，**保留行政区划前缀**、**不剥离行业词**：北京与上海同名不是同一家，「华信科技」与「华信信息技术」也不是同一家
4. 统计每个名称变体出现的文件与次数
5. 输出：主体名清单、写法变体清单、跨文件分布表

聚类结果与名字出现的顺序无关：先按规范核心字号精确分组，再按显式规则跨组合并——两组之间每一对名字都互为同一主体时才合并。同一批文档换个 `--files` 顺序跑，分组不变。

判定规则：

- 同一主体出现两种及以上写法变体 → 标记为「主体名称写法不统一」，置信度为确定
- 存在两个及以上不同核心字号的主体，且未由文件名或章节标题显式区分 → 标记为「疑似混主体」，置信度为疑似，需人工核实
- 「显式区分」**按主体逐一判定**：文件名提到甲公司只说明甲公司被区分了，文件里的乙公司仍无依据，仍要列入疑似清单；只有文件名与章节标题把每个主体都点明，才不报
- 某个主体名在单个文件内出现，且同文件其他位置出现不同主体名 → 同样列入疑似清单

用户不声明主体分组，因此上述混主体判定不可能升级为确定结论。这是本工具的已知边界，报告附录中说明。

## 6. 阶段②：语义检查

### 6.1 分片设计

chunk.py 按段落聚合成分片，单片字符上限约 3000。分片里的 `file` 是**文件标识**：
不同目录下同名的文件（两个 `report.docx`）会被分配成 `a/report.docx` 与
`b/report.docx`，靠它区分，否则一份文档会从报告里消失、每条问题还会重复一遍。
finding 的 `file` 与分片的 `file` 一致。

每一片包含：

```json
{
  "chunk_id": "f1:c3",
  "file": "a.docx",
  "section_path": "第三章/3.2 报价说明",
  "kind": "paragraph | table",
  "text": "……",
  "style": {"font": "宋体", "size": 10.5, "bold": false, "align": "both",
            "indent_first": 2, "line_spacing": 1.5},
  "neighbors": {"prev": "……", "next": "……"},
  "entities": ["北京华信科技有限公司"],
  "numbers": ["1,200.00", "15%"],
  "citations": ["[3]", "如图3-1所示"]
}
```

`section_path` 让报告能给出人类可读的位置而不是只有段序。`neighbors` 提供前后文，供前后矛盾判定使用。`entities`、`numbers`、`citations` 是脚本预标注的结果，智能体只负责判断这些实体的用法是否正确，不必自己寻找实体。这既降低漏报率，也保证不同智能体做的实体识别结果一致。

### 6.2 语义层检查项

语义层承担九类判断：

1. 错别字、别字、形近词误用
2. 标点与空格使用不规范
3. 前后矛盾 — 同一事实在文档两处描述冲突
4. 主体串写 — 句子或段落中出现疑似属于另一主体的名称或信息
5. 引用张冠李戴 — 引用处的语境与被引内容的主题不符
6. 待补充项 — 「详见附件」「见后文」、缺失数据、空白字段、明显应当附带的资质材料
7. 数字逻辑 — 合计与分项不符、比例关系不成立
8. 表述不清或语义歧义
9. 术语前后表述不一致（同义异形混用）

### 6.3 置信度分级

| 置信度 | 含义 |
|---|---|
| 确定 | 有程序化依据，或有文档内明确证据链 |
| 疑似 · 需人工核实 | 仅由模型语义推断，或依赖外部事实 |

阶段①产出的格式与体例类问题一律为「确定」。主体名相关问题中，「同一主体存在多种写法变体」为「确定」，「疑似混主体」依赖聚类推断，标为「疑似 · 需人工核实」。

阶段②的问题分两种情况：

- **确定**：能指出文档内的证据链——两处互相冲突的原文、合计与分项算出来对不上、段落里的名称与全文主体不符等。
- **疑似 · 需人工核实**：判断依赖文档之外的事实——企业名称是否真实存在、引用的文献是否真实存在、法规是否现行有效。

**不要求阶段①有对应依据。** 阶段①只做格式与体例检查，它不产出前后矛盾、错别字、引用张冠李戴这些语义类别；拿阶段①当门槛，会让语义层永远无法给出「确定」，把本可确定的发现全部降级成「疑似」。报告中两类分栏展示，不混同。

## 7. 严重级别

| 级别 | 定义 | 例子 |
|---|---|---|
| P0 | 硬伤，可能导致废标或事实错误 | 混主体、金额合计错误、引用了不存在的编号 |
| P1 | 严重问题，影响评审判断 | 前后矛盾、错别字导致含义改变、法规引用过期 |
| P2 | 体例与格式不一致 | 字体字号不统一、图表题注写法混用 |
| P3 | 优化建议 | 表述可更精炼、术语未给全称 |

级别判定标准写入 `references/severity.md`，智能体在阶段②读取，保证不同智能体的定级口径一致。

## 8. 阶段③：HTML 报告

### 8.1 形式

单个 HTML 文件。CSS 内联在文件内，不引用任何 CDN 或外部字体，不依赖任何 JavaScript 库。需要交互的部分（折叠、筛选）用原生 `<details>` 与少量原生 JavaScript 实现。文件可离线打开、可邮件附件发送、可长期归档。

附 `@media print` 样式，保证打印后分页正常。

### 8.2 章节结构

```
§0 检查范围与未能检查项
   列出全部受检文件及类型、页数或字数、段落数、表格数、推断出的主体名。
   抽取失败的文件在此列明，并给出失败原因。

§1 结论概览
   严重级分布条、类别分布、每文件问题数、两项重点提示
   （疑似混主体数量、待补充项数量）。

§2 硬伤速览
   仅列 P0 与 P1，每条一行：文件 · 位置 · 一句话问题。
   目的是让审阅者只读这一节就能定位致命问题。

§3 按文件明细
   每个文件一节。节首是文件摘要（规模、结构、主体名）。风格指纹是全文口径，出现在 §4.1，不在每个文件里重复。
   其下按类别分组列出问题卡片，每张卡片包含：
   严重级徽章、类别标签、位置（章节路径 + 段序，或表格行列）、
   原文摘录并在问题片段处高亮、问题描述、修改建议、
   置信度标签、来源标签（确定性 / 模型）。
   finding 的 quote 就是有问题的那一段，卡片里用 <mark> 把它标出来；
   来源标签与位置类型都是中文（确定性 / 模型、全文（整篇）/ 段落 / 表格 / 章节），
   报告里不出现英文枚举。

§4 一致性差异专章
   4.1 字体字号差异表
   4.2 段落格式差异表
   4.3 体例差异表（标题层级、图表题注、表格、列表、引用、数字单位）
   4.4 主体名分布与写法变体表

§5 待补充与待核实清单
   勾选式表格，每行包含位置、缺失内容、为何需要。

§6 复查对比
   仅在使用 --baseline 时出现。分新增、已修复、未修复三张表。

§7 附录
   检查规则清单与判定标准、本工具的能力边界声明、
   受检文件的 SHA256 指纹、脚本版本号。
```

## 9. 深度档位

| 档位 | 阶段① | 阶段② |
|---|---|---|
| quick | 全量确定性检查 | 仅错别字与标点扫描 |
| standard | 全量确定性检查 | 九类语义检查全做 |
| deep | 全量确定性检查 | 逐段细读，分片字符上限下调，邻接窗口加大，跨片对照加强 |

默认 standard。档位不同会改变分片参数，也会改变阶段②给智能体的工作量。报告的附录中明确写出本次使用的档位，以及该档位未覆盖的内容，避免读者误解检查范围。

## 10. 复查与基线对比

每次运行结束时，render.py 额外写出一份机器可读的 JSON 结果，包含全部问题的稳定指纹。稳定指纹由「文件标识 + 类别 + 位置 + 归一化后的原文片段」哈希得到，因此同一问题在文档未改动时保持稳定。

下次运行时加 `--baseline <上次 JSON>`，脚本对比出三类：新增、已修复、未修复。报告 §6 按三类分表呈现。

manifest.json 同时记录受检文件的 SHA256。若下次运行时指纹不同，说明文档已改动，此时基线对比结果会额外标注「文件已修改，部分对比结果可能不适用」。

这份 JSON 带一个格式版本标记（`format_version`）。确定性层的问题也写在里面，与模型层的一起对比。旧版本写出的基线里没有确定性层的问题（连 `issues` 键都没有），拿它对比确定性层只会得到「今天跑出来的确定性问题全是新增」——文档一个字没改也不该这么说。因此当基线不带确定性层的数据时，§6 只对比语义层，并写明「基线来自旧版本格式，确定性层问题无法对比」。

## 11. 安装器

### 11.1 安装流程

install.ps1 与 install.sh 执行同样的步骤。两者只在 shell 语法上不同：第 5 步由两个脚本
共同调用 `install/install_skill.py` 完成，一致性是结构保证的，不靠人记得同步。

1. 环境自检与解释器选择。候选解释器按顺序尝试：`py -3.12`、`py -3.11`、`py -3.13`、`python3.12`、`python3.11`、`python3.13`、`python3`、`python`、`py -3`。两个安装器用同一个顺序，因此落在同一个版本上（Windows 上先撞上 `python3` 常常就是 3.13/3.14，「优先 3.11/3.12」的意图就没了）。优先选择 3.11 与 3.12，因为 `lxml` 与 `pdfplumber` 在这些版本上的预编译轮子最完整；3.14 等最新版本常常还没有对应轮子，装依赖会失败。要求版本不低于 3.9。全部候选都不可用则明确报错并给出指引，不静默跳过。
   判定只看两样：退出码必须是 0，标准输出里必须有一行正好是「主.次」。**标准错误上的任何内容都不参与判断**——Windows PowerShell 5.1 会把原生命令的 stderr 变成终止性错误，不特别处理的话，一个只是「启动时提醒一句」的 Python 会被判成没装 Python。
2. 在仓库根目录创建虚拟环境 `.venv`。Windows 路径为 `.venv\Scripts\python.exe`，POSIX 路径为 `.venv/bin/python`。
3. 安装依赖 `pip install -r requirements.txt`。依赖为 python-docx、openpyxl、pdfplumber、lxml。
4. 依赖自检。创建虚拟环境后立即执行一次导入自检，确认 `docx`、`openpyxl`、`pdfplumber`、`lxml` 四个模块均可导入。导入失败则明确报错，包含失败原因与建议的 Python 版本，由用户换用 3.11 或 3.12 重建虚拟环境后重跑安装器。
5. 读取 `install/adapters.json`，逐个智能体适配项：
   - 探测该智能体是否安装在本机，方式是适配项声明的路径是否存在，或其命令是否在 PATH 中
   - 已安装：复制技能运行所需文件到适配项声明的目标目录，写入 `python-path.txt` 指向虚拟环境解释器，改写入口文件，写入适配说明
   - 未安装：跳过，记入「未安装清单」

复制到适配目录的文件集合为：`SKILL.md`、`references/` 全部文件、`scripts/` 全部文件、`requirements.txt`。`docs/`、`tests/`、`install/` 不复制。

**入口文件在安装时被改写**：仓库里的 `SKILL.md` 写的是相对路径（`python scripts/prepare.py`），
那是给在仓库里直接使用的人看的。装到智能体目录后，智能体在用户的工作目录下执行，
相对路径指向的不是技能目录，阶段①必然失败。因此安装时把命令里的解释器（取自
`python-path.txt`）与脚本、规则文档路径（取自技能目录本身）改成绝对路径。入口文件取
仓库原件，**不被适配模板覆盖**：Claude Code 读的是 `SKILL.md`，Codex CLI 读
`~/.codex/skills/<name>/SKILL.md`，`AGENT.md`（单数）不是任何工具认的约定名。

适配模板另存为 `AGENT.md`，`{{SKILL_DIR}}` 替换成安装目录的绝对路径，指向装好之后的
这份副本而不是仓库。同时写一份 `AGENTS.md`（复数，工具认的约定名）作为通用指路。

复制是**同步**语义：仓库里删掉的文件会从安装目录里清掉，否则删掉的脚本会永远留在
`~/.claude/skills/doc-check/scripts/` 里。

6. 打印安装结果：已装列表及其路径与用法示例、未装列表、通用兜底指引

### 11.1.1 参数

安装器只接受显式的参数：`--update`（覆盖已安装的副本并清理过时文件）与 `-h/--help`。
拼错的参数直接报错退出（退出码 2），不被静默当成正常安装。`--update` 与直接重跑
效果相同——安装器总是覆盖并清理，只是把这个意图写出来。

### 11.3 通用兜底

未知智能体走 AGENTS.md。仓库根目录的 AGENTS.md 中写明技能的绝对路径、三阶段协议摘要、以及一份可直接粘贴的说明片段。用户把它加进自己的智能体项目说明文件即可使用。

技能目录里也写一份 `AGENTS.md`，内容是指向同目录 `SKILL.md` 的通用指路（解释器见 `python-path.txt`，脚本见同目录 `scripts/`），认 `AGENTS.md` 约定的工具因此也能找到入口。`AGENT.md`（单数）不是任何工具认的约定名，只放本智能体特有的补充说明。

### 11.4 更新

安装器支持 `--update` 覆盖已安装的副本。仓库路径发生变动时，重跑安装器会重写 `python-path.txt` 中的解释器路径。

安装器总是覆盖并清理，所以 `--update` 与直接重跑效果相同；这个参数的作用是把「我要更新」这件事写出来，并让拼错的参数（`--updtae`）报错退出而不是被静默当成正常安装。

## 12. 错误处理与降级

| 场景 | 处理方式 |
|---|---|
| 单个文件抽取失败（损坏文件、加密 docx、扫描版 PDF） | 记入 manifest.failures，报告 §0 列明未能检查的文件与原因，其余文件继续处理 |
| 扫描版 PDF 无文本层 | 明确标注「需 OCR，当前不支持」，不做任何内容判定 |
| 依赖缺失 | check_env.py 指名缺失的依赖并给出安装命令 |
| 虚拟环境解释器路径失效 | 提示重跑安装器，并回显 python-path.txt 中的实际路径 |
| findings.json 格式非法 | render.py 校验 schema，指出具体哪一条不合法并跳过该条，退出码非零 |
| 智能体无脚本执行权限 | 走 md 与 txt 路径，格式类检查项统一标注「不可自动判定」 |
| 文档规模超出上下文 | 按分片顺序增量处理，findings 分批落盘 |
| 所选档位覆盖不足 | 报告附录写明本次未做的检查内容 |

## 13. 测试策略

单元测试与端到端测试进 CI，模型层评估另行进行。

**样本**：`tests/samples/` 提供含故意埋错的样本文件。docx 样本包含错别字、混主体、字体字号不一致、图表题注写法混用；xlsx 样本包含表头不一致、数字格式混用、金额合计错误；另有 pdf 与 md 样本。pdf 样本由 reportlab 生成，reportlab 是开发依赖（`requirements-dev.txt`），只装 `requirements.txt` 的环境跑不了 PDF 相关测试——此时跳过必须是**看得见的**（明确的跳过原因），不能静默跳过让人以为测过了。

**单元断言**：docx 字体与样式读取正确；主体名变体聚类命中预期；元与万元混用命中；xlsx 数字格式混用命中；分片长度不超过上限；分片带齐 section_path 与 neighbors。样本本身的二进制内容也要断言：docx 样本里埋的字体缺陷（仿宋 10.5pt 对正文宋体 12pt）必须还在，只比抽出来的文本比不出来。

**端到端断言**：使用固定的 findings.json 渲染 HTML，断言各章节存在、严重级统计数字一致、§4 差异表行数与输入一致。负对照要打在**只有那条发现才有**的文字上：§7 规则表里的类别名恒在，断言它等于没断言。

**安装器的行为测试**：安装器是同事拿到仓库后第一个跑的东西，必须按行为测，不按源码里的字符串测。测试在临时的 HOME 与临时的仓库副本上跑真实的安装脚本，覆盖：Windows PowerShell 5.1 下 stderr 有话但能用的解释器必须被接受；标准错误上的版本号不参与判定；一个 Python 都没有时两个安装器都不留下任何东西；两个安装器挑到同一个候选解释器；拼错的参数报错退出；`install.ps1` 带 UTF-8 BOM 而写出来的文件不带；`install.sh` 没有 CR 且带可执行位；装好的入口文件里的命令带绝对路径，且从任意工作目录跑都能出结果。

**模型层评估**：模型输出有不确定性，不进 CI。改用金标评估。准备一批人工标注的样本文档，统计模型在该批样本上的召回率与误报率，评估方法与结果记录在 README 中，作为后续调整规则与提示词的依据。

## 14. 已知限制

- 不核实外部事实。企业名称真实性、引用文献存在性、法规现行有效性均无法判定，相关结论标为需人工核实。
